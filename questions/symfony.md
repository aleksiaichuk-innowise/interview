# Памятка для собеседования: Symfony & Backend Ecosystem

## 🟢 Уровень: Junior (Основы и база)

| # | Вопрос | Ответ |
| :--- | :--- | :--- |
| 1 | **Что такое Autowiring?** | Автоматическое внедрение зависимостей в конструктор на основе типов (Type-hint). Symfony сама находит нужный сервис в контейнере. |
| 2 | **Service Container** | Объект (PSR-11), управляющий созданием и конфигурацией всех служб (сервисов). Реализует паттерн Dependency Injection. |
| 3 | **public: true vs false** | `false` (по умолчанию) — сервис доступен только через DI. `true` — можно достать через `$container->get()`. Приватные сервисы позволяют оптимизировать контейнер. |
| 4 | **persist() vs flush()** | `persist()` ставит объект "на учет" (Unit of Work), `flush()` выполняет накопленные SQL-запросы в БД одной транзакцией. |
| 5 | **Entity Relationships** | Способы связи таблиц: OneToOne, ManyToOne, OneToMany, ManyToMany. Описываются атрибутами (аннотациями) в классе сущности. |
| 6 | **Что такое Voter?** | Класс для централизованной проверки прав доступа (например, "может ли этот юзер редактировать этот пост"). |
| 7 | **Hydration (базово)** | Процесс превращения сырых данных из SQL-запроса в объекты сущностей (Entities). |
| 8 | **MySQL vs GraphQL** | MySQL — реляционная БД. GraphQL — это слой API, позволяющий клиенту самому выбирать, какие поля он хочет получить. |
| 9 | **Что такое Redis?** | Быстрое In-memory хранилище (ключ-значение). Чаще всего используется для кэширования и хранения сессий. |
| 10 | **RabbitMQ: Очередь** | Буфер, где хранятся сообщения до тех пор, пока их не заберет и не обработает Consumer. |
| 11 | **Что такое Dead Letter Exchange?** | "Обменник для писем-ошибок", куда RabbitMQ пересылает сообщения, которые не удалось обработать. |
| 12 | **Зачем нужен CI/CD?** | CI автоматизирует тестирование и сборку кода при пуше, CD автоматизирует выкатку кода на сервер. |
| 13 | **Что такое Kubernetes?** | Оркестратор для управления контейнерами (Docker). Следит за их запуском, масштабированием и доступностью. |
| 14 | **Clickhouse (базово)** | Колоночная БД. Идеальна для аналитики и логов, так как очень быстро считает агрегаты (SUM, AVG) по миллионам строк. |
| 15 | **Зачем нужен .env?** | Файл для хранения переменных окружения (пароли БД, ключи API), чтобы не "хардокодить" их в коде. |

## 🟡 Уровень: Middle (Практика и механизмы)

| # | Вопрос | Ответ |
| :--- | :--- | :--- |
| 1 | **Как работает Unit of Work?** | Паттерн, отслеживающий изменения всех объектов. В конце запроса он сравнивает текущие состояния с исходными и генерирует минимальный набор SQL. |
| 2 | **Lifecycle События** | `kernel.request` (старт), `kernel.controller`, `kernel.view` (если не Response), `kernel.response` (модификация ответа), `kernel.terminate`. |
| 3 | **Hydration: Object vs Array** | `HYDRATE_ARRAY` быстрее и ест меньше памяти, так как не создает объекты и не добавляет их в Unit of Work. Полезно для Read-only списков. |
| 4 | **Owning side в Doctrine** | Сторона связи, где физически лежит FK (внешний ключ). Только изменения на этой стороне сохраняются в БД. |
| 5 | **Voters: методы** | `supports()` (проверяет, относится ли право к данному объекту) и `voteOnAttribute()` (сама бизнес-логика проверки). |
| 6 | **RabbitMQ: Routing Keys** | Строки-метки, по которым Exchange понимает, в какую именно очередь направить сообщение (Direct, Topic). |
| 7 | **Redis: Стратегии кэша** | Cache Aside (сначала в кэш, если пусто — в БД и запись в кэш) или Write-Through (запись сразу в кэш и БД). |
| 8 | **Clickhouse: Колоночное хранение** | Данные каждой колонки лежат в отдельном файле. При запросе читаются только нужные колонки, что дает огромную скорость на аналитике. |
| 9 | **K8s: Pod vs Container** | Под — минимальный объект в K8s. В поде может быть несколько контейнеров, имеющих общий IP и тома (Volumes). |
| 10 | **CI/CD: Pipeline** | Последовательность шагов: Lint -> Static Analysis (PHPStan) -> Tests -> Build -> Deploy. |
| 11 | **Проблема N+1** | Ситуация, когда для списка из 10 элементов делается 1 + 10 запросов к БД. Решается через `JOIN FETCH` в DQL или QueryBuilder. |
| 12 | **Service Tags** | Позволяют пометить сервис (например, `kernel.event_listener`), чтобы Symfony автоматически зарегистрировала его в нужном месте. |
| 13 | **MySQL: Индексы** | B-Tree индексы ускоряют поиск, но замедляют INSERT/UPDATE. Нужно искать баланс и не индексировать всё подряд. |
| 14 | **RabbitMQ: Ack/Nack** | Подтверждение обработки сообщения. Если Consumer упал без Ack, RabbitMQ вернет сообщение в очередь. |
| 15 | **Doctrine Migrations** | Инструмент версионирования схемы БД. Позволяет безопасно обновлять структуру таблиц на продакшене. |

## 🔴 Уровень: Senior (Архитектура и Troubleshooting)

| # | Вопрос | Ответ |
| :--- | :--- | :--- |
| 1 | **Compiler Passes** | Позволяют манипулировать определениями сервисов (изменять их, добавлять аргументы) на этапе компиляции контейнера. |
| 2 | **UoW: Change Tracking** | Бывает `Implicit` (по умолчанию, сравнение всех полей), `Explicit` (только измененные вручную) и `Notify` (через слушателей). |
| 3 | **Messenger: Outbox Pattern** | Сохранение сообщения в БД в той же транзакции, что и бизнес-логика, с последующей отправкой в RabbitMQ. Гарантирует "At-least-once" доставку. |
| 4 | **K8s: Graceful Shutdown** | Приложение должно ловить `SIGTERM`, переставать принимать новые запросы и завершать текущие (через `readinessProbe`). |
| 5 | **Clickhouse + MySQL** | MySQL для транзакций (OLTP), Clickhouse для аналитики (OLAP). Синхронизация через Kafka или периодические батч-выгрузки. |
| 6 | **Redis: Cache Stampede** | Когда кэш протухает, сотни запросов летят в БД. Решается через блокировки (Locking) или вычисление кэша "заранее" (Background recompute). |
| 7 | **GraphQL: N+1 (DataLoader)** | В GraphQL N+1 случается часто. Решается через паттерн DataLoader (группировка ID и один запрос в конце итерации). |
| 8 | **Distributed Tracing** | Использование Jaeger или Zipkin для отслеживания пути запроса через все микросервисы (постановка ID в заголовки). |
| 9 | **Infrastructure as Code** | Описание инфраструктуры (K8s манифесты, Helm чарты, Terraform) в виде кода в репозитории. |
| 10 | **Observability** | Три столпа: Метрики (Prometheus), Логи (ELK/Loki) и Трассировка (Jaeger). |
| 11 | **Blue-Green Deployment** | Наличие двух идентичных сред. Новая версия деплоится в "Green", тестируется, и трафик переключается на нее мгновенно. |
| 12 | **MySQL: Isolation Levels** | Read Uncommitted, Read Committed, Repeatable Read, Serializable. Понимание, как они влияют на фантомные чтения. |
| 13 | **Symfony Messenger: Middleware** | Возможность вклиниться в процесс обработки сообщения (логирование, ретраи, транзакции) через кастомные Middleware. |
| 14 | **Doctrine: Lazy Loading** | Связанные сущности грузятся только при обращении. Опасно в циклах (вызывает N+1). На Senior уровне нужно уметь заменять на Eager Loading. |
| 15 | **Performance Profiling** | Использование Blackfire или Tideways для поиска узких мест в коде и запросах к БД под нагрузкой. |
